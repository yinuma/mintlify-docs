Speclane-Skills は、仕様駆動開発の作業手順を AI へ伝えるスキル群です。プロジェクトの仕様書や実装を読み、フェーズに応じた作業と確認を進めるために使います。Studio が AI との共通作業環境を提供し、Speclane-Skills がその環境で行う仕様駆動開発の手順を支えます。**このページはSpeclane-Skillsが導入されたプロジェクトを対象としています。**利用できるスキルや呼び出し方は、導入先の AI と設定によって異なります。

## 6つのスキル一覧

<CardGroup cols={2}>
  <Card title="speclane-creator" icon="wrench">
    既存プロジェクトを調べ、仕様書を扱う構成・設定・共通スキルの配備を整える入口スキルです。
  </Card>
  <Card title="project-researcher" icon="magnifying-glass">
    仕様書・コード・テストを調べ、仕組みや変更の影響範囲を根拠付きで報告するスキルです。
  </Card>
  <Card title="grilling" icon="comments">
    未決事項を質問に整理し、業務の背景と判断理由を確認する対話を支援するスキルです。
  </Card>
  <Card title="specs-creator" icon="file-pen">
    合意した業務ルールと受入シナリオを正本仕様にまとめ、更新と内容の検査を行うスキルです。
  </Card>
  <Card title="feature-coder" icon="code">
    仕様とコードの変更を照合しながら、テストと実装を小さな単位で進めるスキルです。
  </Card>
  <Card title="bdd-verifier" icon="circle-check">
    正本仕様から期待する動作を拾い直し、テストの網羅性と実行結果を検証するスキルです。
  </Card>
</CardGroup>

<Warning>
  利用できるスキルは、プロジェクトへの導入状況と実行環境の設定によって異なります。スキル名を指定しても、未導入の環境では動作しません。導入状況は担当者またはプロジェクトの設定ファイルで確認してください。スキルを指定するだけで操作権限が増えたり、すべての安全性が保証されたりするものではありません。
</Warning>

## speclane-creator — 準備する

**役割:** 既存プロジェクトを調べ、仕様書を扱うためのディレクトリ構成・設定ファイル・共通スキルの配備を整えます。既存の資産から仕様化を始める場合の入口としても使います。

**使うタイミング:** プロジェクトに Speclane-Skills を初めて導入するとき、または仕様化の環境をゼロから整備するとき。すでに準備済みのプロジェクトで小さな変更を行う際は、毎回このスキルを実行する必要はありません。

**プロンプト例:**

```text
speclane-creatorを使って、このプロジェクトに仕様駆動開発の
環境を整備してください。既存のREADMEとディレクトリ構成を
参照し、配備に必要な設定を報告してから作業を開始してください。
```

**出力の確認ポイント:** 作成・変更されたファイルの一覧、設定の内容と意図、次に行うべき手順の案内が含まれているか確認します。

## project-researcher — 調べる

**役割:** 仕様書・プログラムコード・テストを読み込み、現在の仕組みや変更の影響範囲を出典付きで報告します。「今どう動いているか」「どこを変える必要があるか」を明確にするために使います。

**使うタイミング:** 実装や仕様変更の前に現状を把握したいとき。調査だけを依頼した場合は、仕様書やコードを変更する段階へは進みません。

**プロンプト例:**

```text
project-researcherを使って、予約の取消期限に関するロジックが
仕様書とコードで一致しているか調べてください。
今回は調査結果の報告だけをお願いします。変更は行わないでください。
```

**出力の確認ポイント:** 調査対象のファイル名と該当箇所、仕様書とコードの対応関係、未確認事項のリストが含まれているか確認します。

## grilling — 決める

**役割:** 未決事項を質問として整理し、業務の背景・判断理由・例外条件を確認する対話を支援します。推測で仕様を埋めず、保留した事項も記録することで、チームの合意形成を助けます。

**使うタイミング:** 要求をヒアリングして仕様化を始める前、または仕様書に曖昧な箇所が残っているとき。

**プロンプト例:**

```text
grillingを使って、「予約取消」機能の未決事項を質問として
整理してください。取消できる期限、操作できるユーザーの種類、
期限切れ後のエラーメッセージについて確認が必要です。
```

**出力の確認ポイント:** 質問のリスト、各質問に対して業務上の判断が必要な理由の説明、保留事項の記録が含まれているか確認します。

## specs-creator — 仕様にする

**役割:** grilling などで合意した業務ルールと、前提・操作・期待する結果を記した受入シナリオを、チームの判断基準となる正本仕様にまとめます。仕様書の更新と内容の整合検査を行います。

**使うタイミング:** 業務ルールと受入条件の合意が取れたあと、それを正式な仕様書として文書化するとき。仕様書の更新とプログラムコードへの実装は**別の作業**です。

**プロンプト例:**

```text
specs-creatorを使って、今合意した予約取消のルールを正本仕様に
まとめてください。受入シナリオには「期限内の取消」「期限後の
取消試行」「管理者による強制取消」の3ケースを含めてください。
```

**出力の確認ポイント:** 合意した業務ルールがすべて反映されているか、受入シナリオが具体的な操作と期待結果を含んでいるか、保留事項が明記されているかを確認します。

## feature-coder — 実装する

**役割:** 正本仕様とプログラムコードの変更を照合し、両者の整合を取ります。小さな動作単位でテストと実装を進め、検証できた変更を「確認待ち」の状態へ移行します。

**使うタイミング:** 仕様が合意・文書化されたあと、実際のコード変更を行うとき。**実装する対象を明示して依頼してください。**

<Accordion title="実装を開始するタイミングについて">
  対象と作業内容を明示して依頼するか、AI が提示した実装候補を選ぶと実装が開始します。仕様の完成表示や候補の初期選択だけでは開始しません。候補の初期選択は回答ではないため、内容を確認してから選択を送信してください。依頼文と「反映」の使い分けの詳細は [実装を依頼する](/guides/implementation) を参照してください。
</Accordion>

**プロンプト例:**

```text
feature-coderを使って、合意済みの取消期限ロジックを実装してください。
対象は ReservationService の cancel メソッドです。
変更した仕様とコードの整合を確認し、検証結果を報告してください。
```

**出力の確認ポイント:** 変更したファイルと差分の内容、仕様書との対応関係、テストの実行結果、確認待ちに移行した変更の一覧を確認します。

## bdd-verifier — 確かめる

**役割:** 正本仕様から期待する動作を拾い直し、テストがその動作を十分に確認できているか、実行結果がどうだったかを検証します。実装側の「できた」という説明だけに依存せず、独立した根拠を確認します。

**使うタイミング:** 実装完了後に独立した検証を行いたいとき、またはテストの網羅性を確認したいとき。単独で検証を依頼した場合は結果を報告するのみで、仕様やコードの修正を自動で始めることはしません。

**プロンプト例:**

```text
bdd-verifierを使って、予約取消機能の受入シナリオに対して
テストが十分かどうか確認してください。
不足しているテストケースがあれば一覧で示してください。
```

**出力の確認ポイント:** 正本仕様の受入シナリオとテストの対応表、カバーされていないシナリオの一覧、テスト実行結果のサマリーを確認します。

## スキルの呼び出し方

まず何をしたいかを自然な言葉で伝えます。スキル名を添えて依頼することで、対象のスキルを明示的に使うよう指示できます。

<Tabs>
  <Tab title="調査の依頼例">
    ```text
    project-researcherを使って、ユーザー認証フローが仕様書と
    コードで一致しているか調べてください。
    今回は調査結果の報告だけをお願いします。
    ```
  </Tab>
  <Tab title="実装の依頼例">
    ```text
    feature-coderを使って、合意済みのログイン失敗時の
    アカウントロック機能を実装してください。
    変更したコードと仕様の整合を確認し、検証結果を報告してください。
    ```
  </Tab>
  <Tab title="検証の依頼例">
    ```text
    bdd-verifierを使って、ログインフローの受入シナリオに対して
    現在のテストが十分かどうか確認してください。
    修正は行わず、結果のみ報告してください。
    ```
  </Tab>
</Tabs>

AI が次の作業を選択肢で提示した場合は、対象と行うことを確認して選びます。追加条件がある場合は、その回答に含めてください。

## 作業後に確認すること

スキルの実行後は、報告の内容が目的を満たしているかを確認してから次の作業を指示します。

<AccordionGroup>
  <Accordion title="調査（project-researcher）の場合">
    出典ファイルと該当箇所、未確認事項のリストを確認します。調査範囲に漏れがないか、結論の根拠が示されているかを読みます。
  </Accordion>
  <Accordion title="仕様化（grilling / specs-creator）の場合">
    合意したルールがすべて記録されているか、残る保留事項が明記されているかを確認します。受入シナリオが具体的な操作と期待結果を含んでいることを確認します。
  </Accordion>
  <Accordion title="実装（feature-coder）の場合">
    変更内容と仕様書の対応、テストの実行結果を確認します。受入条件を満たしていると判断したら、変更を確定します。
  </Accordion>
  <Accordion title="検証（bdd-verifier）の場合">
    正本仕様の受入シナリオとテストの対応表、未カバーのシナリオ、実行結果のサマリーを確認します。不足があれば追加実装を依頼します。
  </Accordion>
</AccordionGroup>

<Note>
  現行の Speclane-Skills では、AI は確認待ちへの移行までを担当します。履歴への記録（コミット）は利用者が Git ツールで行います。詳細は [変更を確定する手順](/guides/change-lifecycle#確認待ちの変更を確定する) を参照してください。
</Note>
